# 移植到上游 4.125.2 的工作量估算與路線比較

日期：2026-10-24　對象：Windows 移植候選 15（基底 v4.68.2，commit `dff92fd`）→ 上游 v4.125.2（`3e5b2ba`，2026-10-23）
依據：三份唯讀分析（衝突分類、API 斷裂與 Windows 層重疊、測試與投稿路徑），原始摘要在工作階段暫存區 `scratchpad\upstream\estimate\`。數字是估計值，標示為「約」者誤差可達 ±30%。

## 1. 一句話結論

照先例，「整包移植到 4.125.2 再開一個大 PR」幾乎確定會被關閉，而且要花約 3～4 個月的工程量。原作者的公開 repo 是私有倉庫的匯出快照，快照流程開始後 6 個外部 PR 全部被關閉、改由作者在私有端重做並署名；其中 PR #4 就是「以 v4.68.2 為基底的 Windows 大 PR」，被以「基底太舊、差異太大」關閉。建議改走「先開 issue、以作者要求的 adapter 形式拆小片」，並把現有移植以 fork 形式公開。

## 2. 上游這 16 天改了什麼（v4.68.2 → v4.125.2）

- 611 檔、+73,498／−5,696 行；hub/lib 從 34 個模組擴到約 200 個。
- 五個橫切的架構變化，每一個都和我們的移植正面相撞：
  1. **多語系**：上游自建 `lib/locale.js lt()`＋前端 `HubI18n`＋`langpacks/zh-TW/`；我們自建 `public/i18n.js L()`＋`locales/zh-TW-*.json`。兩套互斥，只能留上游那套。
  2. **server.js 路由抽出**：111 個內聯處理器搬進 41 個 `lib/routes/*.js`＋`lib/engines/*`；我們的 Windows 分支要分散重寫進去。
  3. **app.js 拆檔**：2547 行拆成 1071 行＋13 個 `app-*.js`；我們的原生審批、手動交接、Windows 資料夾等 UI 改動要逐一搬家。
  4. **上游自己的 Windows 層**：WebView2 專用窗、`lib/platform/win32*`（程序所有權、native write-through rename、killTree）、`owned-processes`、SQLite 更新槽、授權儲存、`start-windows.js`（硬性要求 Git Bash）。但 README 明寫「隔離實行の Windows 未対応は既存のまま」，procwatch 在 Windows 停用，`processCwd` 回空。也就是說，**我們移植的核心（AI CLI 在 Windows 上的隔離執行與監看）上游目前刻意不做**。
  5. **付費邊界**：`delegate`、`queue_auto`、`limit_switch`、`webchat`、`parallel` 五項是付費功能；授權強制、30 天試用、離線只剩基本對話；`webchat` 是付費擴充的 id（公開樹是 404 樁），ChatGPT 貼上路徑已廢止。我們的委派、web-chat、Claude＋Grok 同時執行都踩在這條線上。

## 4. 做完之後會怎樣（投稿面）

- 公開 repo 不是就地開發，`scripts/export-public.js` 只匯出已提交檔案、不帶歷史、排除 `hub/paid/`。外部 PR 不會被直接 merge；作者的模式是「關閉 PR、在私有端重做、CHANGELOG 署名」。
- 作者對 Windows PR 的明示要求（PR #3，10/19）：專用 Windows adapter、不要全域相容補丁、保留 Mac 行為；小步提交，順序是「換行與 CLI 解析 → 持久化 → 程序擁有權」；程序擁有權用 CIM 驗 PID＋建立時間＋執行檔＋SID，禁止只靠 PID 的 taskkill；附真機結果與失敗測試；大改動先開 issue。
- 即使照做，我們最有價值的部分（隔離原生執行、Claude／Grok 並行、web-chat 手動交接）一是上游宣告不支援，二是落在付費閘後面，三是 webchat 槽位被私有模組占用。這三塊被原樣接受的機率很低。

## 5. 路線比較

| 路線 | 做法 | 工時 | 被接受的可能 | 風險 |
|---|---|---|---|---|
| A. 整包移植到 4.125.2 再開大 PR（你目前選的） | 第 3 節全部 | 450～630 h | 很低（PR #4 先例） | 做完時上游又前進了；核心功能撞付費閘 |
| B. 先開 issue，照作者要求拆小片 adapter PR | 以 4.125.x 為基底，先做作者點名歡迎的三片：CLI 解析與換行、持久化（fail-closed、MoveFileExW 邊界）、程序擁有權（CIM＋SID）。對應我們的切片 1～3，約 5,600 行要改寫成 adapter 形式 | 第一批約 60～100 h；後續每片 20～60 h | 中（PR #3、#6 的模式：作者吸收並署名） | 隔離執行、並行、web-chat 多半不會被收；作者可能自己重做 |
| C. 以 fork 形式公開現有移植，開 issue 告知並邀請 | 做交付整理（LF 正規化、去掉內部流程痕跡、繁中／英文說明、已知限制、MIT 與署名），推到你的 fork 的分支，開一個 issue 說明 Windows 隔離執行移植、附連結與真機結果，問作者想怎麼收 | 約 20～40 h | 不求被 merge；作者可自行取用 | 分支停在 4.68.2，需自行定期挑選上游修正 |
| D. C ＋ B 並行 | 先做 C 讓成果可見、可用；再視作者在 issue 的回應，逐片做 B | C 的 20～40 h ＋ B 的第一批 | 最高 | 兩條線要同步維護 |

## 6. 建議

走 **D**：先做 C（約一週內可交），在 issue 裡把我們的真機結果、安全模型與已知限制講清楚，問作者是否要以 adapter 形式分片收，以及他對「Windows 隔離執行」的規劃；等他回應再決定 B 要做哪幾片。不建議 A。

不論選哪條，交付整理都要做：LF 正規化（上游 `.gitattributes`）、移除 `r2–r12` 這類內部輪次命名與 `docs/superpowers` 內部規格、補英文或日文的說明、通過上游 `export-public.js` 的 `inspect()` 檢查（不含 email、`/Users/<名>`、token 樣式）。

## 7. 需要你決定

3. 若含 C：fork 要公開在哪個帳號、分支名稱，以及是否保留 `docs/superpowers` 的內部規格。
